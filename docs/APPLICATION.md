# Приложение участника

## Запуск и рабочий сценарий

Требуется Python 3.12. Установка из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/streamlit run app.py
```

1. Выберите контрольный набор и сохраненный пример слева, нажмите «Открыть план».
2. На вкладке «План» измените договоры, инвестиции или заказы; нажмите «Применить изменения». Новые строки добавляются в таблицах. Даты имеют формат ГГГГ-ММ-ДД.
3. «Рассчитать» на вкладке результатов показывает деньги, физический баланс и нарушения. После редактирования или смены сценария старые результаты помечаются устаревшими.
4. Сравните BASE, обязательный стресс и низкий/высокий спрос. Исследуйте рост спроса и порог первого нарушения сервиса/резерва.
5. На вкладке оптимизации задайте отключенные источники и допустимые инвестиции. Найденный план проходит независимую симуляцию; затем его можно принять в редактор или скачать.
6. Сохраните план в локальный каталог `saved_plans/` или скачайте JSON. Загруженный JSON валидируется до замены текущего плана.
7. Выгрузите JSON, ZIP с CSV или XLSX. Все числа берутся из того же объекта результата, что и интерфейс.

Планы локальны для рабочего каталога приложения; авторизация, многопользовательский сервер и облачное развертывание в эту версию не входят.

## Командная строка и API

```bash
.venv/bin/python -m fuel_planner.cli optimize --strategy earth --output saved_plans
.venv/bin/python -m fuel_planner.cli optimize --strategy lunar --time-limit 120
.venv/bin/python -m fuel_planner.cli compare examples/plans/earth.json
.venv/bin/python -m fuel_planner.cli evaluate examples/plans/earth.json --scenario MANDATORY_STRESS --format xlsx --output /tmp/stress.xlsx
.venv/bin/python -m fuel_planner.cli --extra-source --future-year optimize --time-limit 120
```

`--case PATH` выбирает другой каталог той же структуры. Импортируются CSV из `data/` и YAML из `scenarios/`. Контрольные входы не перезаписываются. Приложение предлагает исследовательские копии с Source-X и 2041; CLI допускает отдельные входные каталоги.

Основные Python-интерфейсы:

```python
from fuel_planner.data import load_case
from fuel_planner.engine import evaluate
from fuel_planner.optimizer import optimize, Settings
from fuel_planner.storage import load_plan, export_bytes

case = load_case()
plan = load_plan("examples/plans/earth.json")
result = evaluate(case, plan, "BASE")
solution = optimize(case, Settings(time_limit=120))
xlsx = export_bytes(result, "xlsx")
```

План версии 1 содержит `plan_id`, `scenario_id`, `decisions`, `assumptions`, `description`. Четыре раздела решений соответствуют оболочке организатора. Заказы содержат источник, дату заказа, дату поступления, валовой объем и отметку стартовой партии. Договор содержит год, годовую резервируемую мощность, начало и исключительную конечную границу периода в днях. Для источника разрешен один договор в год. Инвестиции имеют код, дату реализации/финансирования и отдельную необязательную дату оплаты опциона Earth-New.

`evaluate` принимает сценарий явно, поэтому сохраненный `scenario_id` не блокирует сравнение того же плана в другом окружении. Пустой план допустим и дает диагностику неисполнимости. Невалидные типы, неизвестные источники, годы и дубли договоров отклоняются с объяснением.

Результат сохраняет все обязательные поля `schemas/export.schema.json`, версии ПО, fingerprint полного набора и допущения. Время запуска намеренно не включается в вычисляемое содержимое, чтобы одинаковые входы давали одинаковый результат.

## Реестр допущений

Каждый пункт ниже — TEAM_ASSUMPTION, если это не повторение явно указанного контрольного правила.

| Пункт | Принятое значение и область действия |
|---|---|
| Календарь | 365 дней на год, без 29 февраля; равномерное потребление |
| Перевод lead time | Неделя = 7 дней, месяц = 365/12 дней, округление срока вверх; верхняя граница диапазона по умолчанию, lower доступен через план |
| Начальные договоренности | Предварительные заказы до 2035 разрешены для доступных на начало горизонта каналов; фактическая поставка не раньше доступности |
| Стартовый запас | Идентифицированная партия в первый день до проверки резерва и до потребления; платится по цене и договору первого года, попадает в валовое поступление один раз |
| Финансирование старта | Обязательное текстовое основание в плане; отдельный источник финансового капитала количественно не моделируется, поскольку исходник не содержит общего денежного бюджета закупок |
| Резерв | Только физический запас; 45 дней общего спроса, проверка на начало года. Начальный startup — специальная граничная операция |
| Earth-New | 18–24 месяца — подготовка после реализации опциона; повторные партии после ввода имеют даты по договору, без повторного начисления 24 месяцев |
| Lunar-ISRU | После финансирования до 2038 ввод с 2038; первый заказ не раньше ввода и первая поставка спустя 1–2 месяца |
| ZBO | Действует с даты оплаты, не раньше 2036; дополнительный строительный срок исходником не задан |
| Capacity | Годовой договорный объем; произвольный объем партии в пределах годового договора и физической емкости, без придуманного суточного лимита канала |
| Платежи | По году планового поступления; оплаченный заказ не уменьшается при риск-недопоставке. При задержке фактический физический поток переносится, платеж остается в договорном году |
| TOP и резервирование | TOP один раз за договорный период. Периодическое право = annual capacity × доля года. Отдельная годовая reservation fee пропорциональна периоду |
| Хранение | За каждый день среднее запаса после приема и перед следующим днем; holding rate × средний запас / 365 |
| Переполнение | Избыточная валовая партия отклоняется с `STORAGE_OVERFLOW`; оплаченный заказ сохраняется. Принятое поступление, отклонение и потери показаны раздельно |
| Критический спрос | Обслуживается первым; сервис = 1 при нулевом спросе |
| Emergency | Любая плановая закупка считается базовым использованием для лимита двух последовательных лет. Контингентная активация допускается только в отдельном risk scenario |
| Терминальный запас | После последнего года обязательный конечный запас не задан; оптимизатор может его исчерпать |
| Экономика | Недисконтированные расходы, без выручки и денежных штрафов за срыв миссии |
| Reliability | Metadata для отдельного исследования; не множитель BASE или mandatory stress |
| Риски | Интервальные сценарии без вероятностей; эффект меры показывается при измененной задержке/доле поставки, расходы на меру не включены |
| Численная точность | Проверки физических ограничений с абсолютным допуском 1e-6; сверка objective с симулятором max(1e-5, стоимость × 1e-8) |

Расчет сохраняет предписание организатора об annual capacity; он не доказывает физическую реализуемость произвольного космического рейса вне агрегированной модели. Стоимость условная, не рыночная.

## Оптимизатор

Используется SciPy `milp` с HiGHS. Цель — минимизировать закупку, годовое резервирование, хранение, OPEX и CAPEX при 100% обслуживании BASE. Поставки и остатки — непрерывные переменные на каждый день; инвестиции и годы базового Emergency — бинарные. Модель не дробит TOP на месяцы.

Режим хранения представлен отдельными потоками до/после ZBO; бинарные ограничения запрещают использовать пониженные потери без инвестирования. Остаток плюс дневное потребление проверяется против емкости до расходования топлива.

Дата автоматической инвестиции — 1 января. Earth-New оплачивает 90+270 в выбранном году и готов через верхнюю границу срока. Lunar-ISRU финансируется в 2037; при недисконтированных расходах и вводе в 2038 более ранняя оплата не улучшает целевую функцию. ZBO доступна с 2036. Ручной план допускает раздельные оплаты опциона и внутригoдовые даты.

По умолчанию лимит 120 секунд, относительный зазор 0.001. UI и CLI показывают статус, objective, нижнюю границу, время и зазор. Найденный к лимиту план не объявляется точным оптимумом. Решение принимается только при независимой проверке полного сервиса, жестких ограничений и совпадения стоимости.

Минимум установлен только для этой области поиска. BASE optimum не означает устойчивость к стрессу. Низкий спрос способен вызвать переполнение, высокий — дефицит; такие результаты являются частью анализа, а не ошибкой интерфейса.

## Проверка и расширяемость

```bash
.venv/bin/python -m pytest -q
.venv/bin/python tools/validate_reference_repo.py --participant
.venv/bin/python tools/build_examples.py
```

Тесты охватывают V01–V10, баланс каждого дня, timing, TOP, CAPEX, прoрацию, все mandatory shocks, отдельный риск, аналитический optimum маленькой задачи, неисполнимость, лимит времени, сериализацию, экспорт и интерфейс Streamlit AppTest. CI повторяет проверки на Python 3.12.

`research_case` копирует входы: Source-X имеет собственную строку источника и проходит те же формулы; 2041 содержит явно заданный спрос +5%. Конечные CAPEX/stress-лимиты после 2040 не продлеваются автоматически. Физические annual constraints и сервисные требования для расширения принимаются как допущение команды.

Научные ссылки организатора сохранены в [SCIENTIFIC_BASIS.md](SCIENTIFIC_BASIS.md); приложение не претендует на независимую проверку недоступных первичных документов. Факты о неполноте комплекта описаны в [ERRATA_AND_PROVENANCE.md](ERRATA_AND_PROVENANCE.md).
